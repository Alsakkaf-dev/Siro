00ملخص تنفيذي

باختصار: وش بنبني، وكيف، وبأي ترتيب.

الفكرة

موقع شخصي واحد يشتغل على جهازك (http://127.0.0.1:4310)، فيه «Shell» واحد (قائمة، بحث، تقويم، إشعارات) و«نواة» مشتركة (قاعدة بيانات، ملفات، أحداث). كل منصة = Plugin يركب على النواة بعقد (Contract) ثابت، فأي منصة جديدة مستقبلاً تنضاف بدون ما تخرب اللي قبلها.

القرار التقني

Vite + React (SPA) + Express على 127.0.0.1 + SQLite (better-sqlite3 + Drizzle) + chokidar، مع pdfjs-dist وdocx-preview وVideo.js، وTailwind 4 + shadcn بوضع RTL، وخطوط Cairo وIBM Plex Sans Arabic. يشتغل على Windows بأمر واحد وما يطلع من جهازك شي. البديل الأخف: صفحة HTML ثابتة + JSON + سكربت Python صغير.

المنصات الأولى

  • الأكاديمية: كل الفصول ← المواد ← التقييمات، حاسبة درجات، Timeline، Heatmap للأسابيع 1–16.
  • المكتبة: مكتبة افتراضية بغرف (فصول) ورفوف (مواد) وأدراج (أنواع الملفات)، عارض PDF/صور/مستندات، ومشغل فيديو (YouTube + فيديوهات على الجهاز).
  • الحياة: المال (صناديق)، الروتين، المهام، كسر العادات، الصحة، الصلاة والقضاء، والرياضة (خريطة عضلات، تمارين، خطط، تقدم).

الترتيب

6 مراحل: الأساس ← الأكاديمية ← المكتبة ← الحياة ← الرياضة ← الربط والتلميع. تقدير إجمالي ~17–22 أسبوع بمعدل 8–10 ساعات أسبوعياً افتراض (تقدر تسرّع أو تبطّئ حسب ضغط الدراسة). كل مرحلة تطلع بشي تستخدمه فعلاً.

قاعدتان ذهبيتان: (1) ملفاتك تبقى في مكانها على القرص — الموقع «يفهرس» و«يعرض» فقط، ما ينقل ولا يحذف. (2) ملفات راشد وسالي لهم؛ الموقع يقرأ فقط، وأي تعديل يروح لهم كطلب (Command) وهم ينفذونه بأمرك.

01الرؤية والأهداف والمبادئ

ليش نبني هذا الشي أصلاً، ووش يعتبر «نجاح».

الرؤية

اليوم عندك «مركز قيادة» للفصل الخامس (Dashboard فيه المواد والتقييمات والـ Heatmap والحاسبة). الرؤية: نكبّر هذا المركز إلى موقع عملاق يدير كل الفصول (السابقة والحالية واللي بتجي — تضيف الفصل 6 بيدك وتضيف مواده)، وجنبه منصات ثانية للمكتبة والحياة والرياضة، وكلها تتكلم مع بعض: لو أسبوع امتحانات، الجيم يخف تلقائياً؛ لو عندك مذاكرة، تظهر كبلوك في روتينك.

المبادئ الهندسية (Principles)

1 · Local-first

البيانات على جهازك، والموقع يشتغل كامل بدون نت. الإنترنت «إضافة» مو «شرط».

2 · الملفات هي الحقيقة

مجلد الدراسة هو المصدر؛ قاعدة البيانات «فهرس» يقدر يُعاد بناؤه في أي وقت.

3 · مالك واحد لكل بيانات

كل نوع بيانات له كاتب واحد (Single Writer): بيانات راشد يكتبها راشد، والموقع يقرأ.

4 · Plugin Contract

المنصات ما تكلم بعض مباشرة؛ تتكلم عبر النواة (أحداث + API). هذا اللي يخلي الإضافة سهلة.

5 · الصدق في الأرقام

كل رقم معروض عليه وسم: مثبت محسوب افتراض. ما نخترع أرقام.

6 · بسيط أولاً

نبني أصغر نسخة تشتغل (MVP) لكل منصة، ونستخدمها، وبعدين نزيّن. الجمال بعد الفائدة.

خارج النطاق (Non-goals) — حالياً

  • ما فيه حسابات مستخدمين أو استضافة على الإنترنت — الموقع لك وحدك.
  • ما نبني تطبيق جوال الحين (ممكن لاحقاً كـ PWA على شبكة البيت فقط — قرار مؤجل).
  • ما ننسخ محتوى مواقع ثانية (مثل musclewiki) — نستلهم الفكرة فقط.
  • الموقع ما يعدّل التقويم ولا ملفات راشد/سالي مباشرة.

02خريطة النظام (System Map)

ثلاث طبقات: الغلاف (Shell) ← المنصات (Plugins) ← النواة (Core) ← التخزين (Storage).

شكل 1 — خريطة النظام: كل منصة تمر بالنواة، والنواة وحدها تلمس التخزين. الأسهم المتقطعة = مصادر خارجية للقراءة فقط.

عقد المنصة (Plugin Contract)

أي منصة (حالية أو مستقبلية) لازم تصدّر كائن واحد بهذا الشكل. النواة تقرأه وتركّب المنصة تلقائياً في القائمة والبحث والتقويم:

// core/plugin.ts
export interface PlatformPlugin {
  id: "academic" | "library" | "life" | "sports" | string;   // unique
  name: { ar: string; en: string };
  color: string;                         // accent token, e.g. "--acad"
  version: string;                       // semver; bumps run migrations
  routes: RouteDef[];                    // pages under /p/<id>/...
  nav: NavItem[];                        // sidebar entries
  widgets?: WidgetDef[];                 // cards for "Today" / home
  search?: (q: string) => Promise<SearchHit[]>;  // global search provider
  calendar?: (range: DateRange) => Promise<CalEvent[]>; // feeds unified calendar
  on?: Partial<Record<EventType, Handler>>;      // event-bus subscriptions
  emits?: EventType[];                   // declared events (documentation + checks)
  migrations: Migration[];               // own tables, prefixed: acad_*, lib_*, life_*
  settings?: SettingsSchema;             // zod schema → auto settings page
}

قاعدة 1

كل منصة تملك جداولها (Prefix)، وما تكتب في جداول غيرها. تبي شي؟ تطلبه بالـ API أو تسمع لحدث.

قاعدة 2

الكيانات المشتركة (Semester, Course, Tag, File, Event) في النواة، وكل المنصات تشير لها بالـ ID.

قاعدة 3

منصة جديدة = مجلد plugins/<id>/ + سطر في plugins.config.ts. لو عطلتها، الباقي يشتغل عادي.

البديل الأخف (Fallback) — لو تبي تبدأ اليوم

Static HTML + JSON + سكربت Python واحد: ملف index.html (نفس أسلوب الـ Dashboard الحالي) + مجلد data/*.json + serve.py يمسح مجلد الدراسة ويكتب library.json، ويقدم الملفات على http://127.0.0.1:8000 (لازم HTTP وليس file:// عشان YouTube). http.server في Python ما يدعم Range للفيديو الكبير ← يحتاج كود بسيط إضافي.

متى تختاره؟ لو الوقت ضيق أيام الامتحانات. العيب: لما تكبر المنصات (مال، عادات، رياضة) يصعب الحفظ والربط. الانتقال: نفس ملفات JSON تنقرأ لاحقاً في SQLite بسكربت استيراد — ما يضيع شي.

🔒 الشبكة

  • الخادم يستمع على 127.0.0.1 فقط — مو 0.0.0.0 — يعني ما أحد على الشبكة يقدر يفتحه.
  • لا نشر (Deploy) على أي استضافة. لا Vercel، لا Firebase Hosting، لا Tunnel.
  • سياسة CSP تمنع أي طلب خارجي ما عدا نطاقات YouTube المطلوبة للمشغل المضمن في صفحة الفيديو فقط.
  • بدون Analytics أو تتبع.

📁 الملفات

  • Express يقدم ملفات من جذور مسموحة فقط (Whitelist) (مجلد الدراسة، تصدير راشد/سالي) — حماية من Path traversal (..\).
  • المكتبة ما تحذف ولا تنقل ملفاتك.
  • ملفات راشد: قراءة فقط على مستوى الكود (فتح الملف read-only).

🗝️ الأسرار

  • ما فيه كلمات مرور أو مفاتيح API في الكود أو JSON. لو احتجنا مفتاح (مثلاً YouTube Data API لعناوين الفيديو — اختياري) يكون في .env.local خارج Git.
  • config/paths.json وdata/ في .gitignore.
  • لو رفعت الكود على GitHub: Repo خاص، والكود فقط بدون بيانات.

💾 النسخ الاحتياطي

  • نسخة يومية من platform.db (SQLite backup API) إلى backups\YYYY-MM-DD\ مع الاحتفاظ بآخر 14 يوم + نسخة شهرية افتراض.
  • النسخ على قرص خارجي/USB أسبوعياً (يدوي) — مو سحابة للمال والصحة.
  • راشد له نظام نسخ خاص (backups\<date>\) — الموقع ما يلمسه.
  • اختبار استرجاع شهري: «هل النسخة تفتح؟».
خط أحمر: أي ميزة تحتاج رفع بيانات مال أو صحة لخدمة خارجية (حتى «ذكاء اصطناعي» أو مزامنة) = مرفوضة في التصميم. خيار «قفل» اختياري برمز PIN لشاشات المال/الصحة لو أحد يستخدم جهازك.

16ماذا تحتاج لتبدأ

🧰 على جهازك (مرة وحدة)

  1. تثبيت Node.js 24 LTS وGit وVS Code.
  2. تأكد إن المتصفح حديث (Edge/Chrome) لدعم Tailwind 4.
  3. مجلد للمشروع، مثلاً Storage\Platform\app افتراض.
  4. مساحة قرص للـ Thumbnails والقاعدة (عادة أقل من 1–2 GB افتراض).

📋 قرارات منك (10 دقائق)

  1. جاوب Q1, Q2, Q3, Q6 (الأهم لبداية العمل).
  2. وافق على الـ Stack (Vite + React + Express + SQLite) أو اختر البديل الخفيف.
  3. أعط أمرك لراشد بخصوص التصدير (Q8) — متى ما تبي.

🚀 أول أسبوع (P0)

  1. npm create vite@latest web -- --template react-ts + npx shadcn init --rtl
  2. خادم server/ بـ Express 5 + better-sqlite3 + Drizzle، وجدول core_settings.
  3. AppShell بالعربي RTL + قائمة جانبية + صفحة «اليوم» فارغة.
  4. start.bat يشغل على 127.0.0.1.
  5. أول Commit في Repo خاص.

✅ تعريف «بدأنا صح»

تفتح start.bat، يطلع لك موقعك الداكن بالعربي، فيه قائمة «الأكاديمية / المكتبة / الحياة / الرياضة»، وكل منها صفحة «قريباً» — والنت مقطوع. بعدها مباشرة: استيراد SEM 5.

الخلاصة في سطرين

نبني Vite + React + Express + SQLite محلي على جهازك (من http://127.0.0.1)، بنواة مشتركة ومنصات Plugins. نبدأ بالأساس والأكاديمية (البذرة = SEM 5)، ثم المكتبة، ثم الحياة مع احترام قواعد راشد حرفياً، ثم الرياضة ببيانات مفتوحة مرخّصة، وأخيراً الربط الذكي بين الكل.
